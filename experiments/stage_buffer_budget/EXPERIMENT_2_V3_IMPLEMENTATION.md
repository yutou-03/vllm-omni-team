# 实验二 V3：代码修改与验收边界

## 用户要求对应的实现

1. **多请求暂停**：控制器每次按原生 FIFO 等待前缀逐一预留候选，数量由紧急等待数、可用执行名额、安全候选、驻留余量共同决定。`max_concurrent_holds=K` 是上限，不是每次暂停 K 个，更不是固定两个。多个 pending admission 在 KV 分配前也占用预留驻留名额。
2. **纯文本库存**：Thinker 的纯文本 SSE 在前端进入每请求有界 FIFO；独立 producer 持续接收，consumer 按 4.8 token/s 的绝对时钟放行。第一段立即发送，一 token 的显式提前量吸收事件循环抖动；只放行绝对消费时钟已到期的记录，滞后形成的补发债务从安全库存中扣除。接收协程每条消息主动让出事件循环，避免 ready source 与未满队列连续运行饿死放行。所有原始 SSE、token IDs、finish、usage 记录保序原样交付。
3. **库存口径**：只使用前端已接收而未放行的文本，不使用上游生成计数或已发布但未接收的输出。token 数使用同一 tokenizer 对可见文本重新计算；字符和 wire SHA256 验证无丢失、重复或乱序。控制器扣除观察老化、完整 SSE 突发和 tokenizer 边界保护；过期或关闭流不能支持暂停。该库存不是客户端已经收到的数据。
4. **重复暂停与恢复**：V3 允许同一请求恢复后再次暂停，仍受库存、decode checkpoint 和 cooldown 约束。恢复请求按库存保护期限优先获得释放的名额；有待恢复请求时停止新增暂停，待恢复名额优先于新 waiting admission。KV 保持驻留，未引入换出、重算或实验一队列重排。
5. **时长语义**：100ms 仍是单次申请上限，释放申请不等于已经恢复执行。V3 通过显式 `inventory_deadline_lease` 和完整紧急执行预算保护来区分名义 slice 超时与库存保护期限；名义超期仍记录。恢复余量耗尽则停止新增暂停并记录失败，不能将其解释为无断流保证。同步 GPU batch 不可中途打断，预测误差须在真实烟测中验证。
6. **容器生命周期**：一轮仅使用一个 `--rm` worker 容器，各策略切换独立服务进程；代码、参数、日志及结果保存宿主机。退出及异常执行清理。两次启动失败及一次用户要求的中止单独归档，不计实验结果。

## 代码完成后才执行的验证

- CPU：可变 1/3/4 候选、候选不足、驻留预留、同一请求重复暂停、KV 保留、断连回收、完整交付。
- GPU 机制：至少 3 个同时真实暂停；每条均有紧急实际入批、释放、重新执行和新输出；保留 KV；文本库存为正；客户端完整。
- 机制未成立，停止后续性能运行。首先定位实现、库存或同步批次问题，不降低安全阈值制造暂停。
- 第一轮为 K16/R64 纯文本机制验证及单种子试跑；不代表音频双阶段、K64 或正式收益结论。
- 通过后做同轨迹无缓冲无暂停、仅文本缓冲、动态多暂停、固定预算多暂停；报告连续首输出扣分、旧硬门槛和预先冻结的 β 敏感性。
- 当前原生等待顺序保持不变；新增暂停受害者选择及恢复优先只属于实验二机制。

## 当前限制

服务端库存保护依赖预测的同步步骤和紧急执行时长，不是实际墙钟上限保证。K64 需要独立确定执行/驻留配置及足够驻留余量，不能直接将 K16 试跑外推。约20%收益是待检验目标。

## 2026-11-03 首轮 GPU 后的修复

真实 4/4 暂停链及 20/20 客户端文本校验通过，但宽松文本累计断流均值 4.879s，不能作为性能收益。只读复核发现前端曾连续 1.574s 接收642条记录而无任何放行，库存充分，GPU仍继续输出。该轮前缀token数均单调，排除了token计数回退假说。修复主动协作yield、每条只计算一次canonical前缀token数，并使用不随迟到永久重锚的绝对交付时间；补发债务计入安全库存扣减。完整复跑前不报告新收益。

第二轮修复版发现独立缺陷：输出计数与入口线程共用fast tokenizer，发生`Already borrowed`，20条中3条失败，多暂停门槛未通过，整轮排除收益比较。服务初始化阶段创建输出计数专用tokenizer副本，保持相同词表与编码规则，隔离入口的truncation/padding状态。新增多token包及迟到追赶/债务回归用可控时钟验证。
