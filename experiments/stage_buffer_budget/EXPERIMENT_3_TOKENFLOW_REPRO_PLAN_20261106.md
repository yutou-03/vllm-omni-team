## 1 目标与范围

分别在纯文本、纯音频输出场景中近似复现 TokenFlow 的流式 QoS 指标和缓冲感知调度。每个请求只消费一种输出，不进行双输出联合评分或两类请求混合实验。

请求到达服务器时携带目标流速度 r_i，客户端维护已收到但尚未消费的内容缓冲。服务端根据客户端反馈选择工作集、暂停和恢复请求，并强制执行论文 §4.3 的容量约束：

\[
D(t)=\sum_{i\in\mathcal W(t)}r_i\le\widehat\Gamma(t).
\]

r_i 是该请求约定的持续输出需求，不是其当前测得的生成速度。Γ 是相同输出单位下系统当前可持续生成容量的估计。若当前工作集需求超过容量，退出缓冲感知调度，安全退回原生 FCFS 与内存准入。

客户端消费缓冲是唯一库存信用来源。不新增或使用 Q01/Q12 阶段接收缓冲，不使用阶段间 embedding、codec frame、待转换 chunk 库存支持暂停。保留框架模型执行所需的原生传输和 chunk 机制，但其队列不参与缓冲信用计算。

## 3 客户端缓冲与请求速率契约

数据路径分别为：

- 文本：服务端流式文本 → 客户端接收 buffer → 按请求速率显示或模拟阅读。
- 音频：服务端流式音频 → 客户端解码后的 PCM buffer → 按播放时钟消费。

客户端接收与消费独立执行，不通过慢读网络连接模拟消费。服务端正常及时发送输出，不把服务端发送限速形成的库存算作客户端缓冲。

| 模态 | 请求速度字段 | 缓冲与容量单位 |
|---|---|---|
| text | `payload.omni_scheduling.text_consume_rate_tps` | 可见文本 token；r_i、Γ 均为可见 token/s |
| audio | `payload.omni_scheduling.audio_consume_rate` | 有效音频媒体秒；r_i、Γ 均为媒体秒/墙钟秒，正常播放 r_i=1 |

以上速率字段置于支持它们的 schema v2 元数据中，其余必填项须依当前校验器补齐。缺失、非有限或非正速率在实验入口报错；不能静默使用全局 4.8 token/s 或音频等价 3.3 token/s。不同文本请求可携带不同速率；音频第一轮固定 1×，之后单独扩展播放倍速。请求内速率第一轮固定。

音频的媒体秒是对论文 token 单位的显式适配。不能使用任意 audio-equivalent-token 系数判断容量，也不能以 16 路 codec code 数冒充播放需求。若以后改用 codec frame/s，必须固定 frame 与有效播放时长的映射，并使 r_i 与 Γ 同时换算。

反馈至少包含：logical_request_id、attempt/session 标识、单调序号、模态、速率、累计接收量 A_i、累计消费量 C_i、开始消费标记、接收 EOS 标记、消费完成/断连标记、反馈时效信息。

\[
B_i=A_i-C_i,\qquad H_i=B_i/r_i.
\]

文本固定 tokenizer 与可见 token 计量，处理 SSE 分片造成的词边界变化；音频按完成解码且可播放的有效采样计量，去除重复上下文。到达时间、解码就绪时间、首次消费时间分别记录，不能把解码前到达时间当作已经可播放。

服务端按反馈老化保守扣减库存，反馈过期、乱序、跨 attempt、单位不符或断连时没有暂停信用。首轮允许同机共享时钟及反馈通道；跨主机不能直接相减两端 monotonic 时钟，需明确时钟映射或使用含传输延迟上界的协议。没有新反馈不等于消费停止。

EOS 到达后仍要排空客户端 buffer，停止生成与完成消费是两个事件。服务端已完成该输出的请求可退出计算工作集，但消费轨迹继续计入延迟、完整率和排空时长。

## 4 工作集及容量估计

### 4.1 工作集口径

W 是已准入且仍需要生成内容的逻辑请求集合，包括正在执行、被缓冲策略暂停、等待后续输入 chunk 的请求。暂停不能把请求从 W 中删掉；同一音频请求在三个阶段只计一次需求。已接收但尚未准入的请求位于全局等待队列，不属于 W。

区分执行 batch、KV 驻留集合和 W。三个集合不能互相代替。客户端已收齐内容但尚未消费完的请求不再产生新的计算需求。

每次准入、完成、取消、容量更新和调度周期均检查容量；准入预留原子更新，防止多个并发准入分别检查成功但合计越界。

### 4.2 Γ 的估计

纯文本、纯音频分别估计 Γ，不跨模态相加，不把请求到达率 QPS 当作 Γ。

先在独立校准负载中得到不同请求长度、批大小、prefill/decode 组成、硬件配置下的可持续端到端输出容量。在线用实际执行记录与当前请求特征更新，硬件利用率作为辅助特征。估计必须计入真实 prefill、调度、抢占恢复和周期内的等待开销，不能只统计最快的 decode 瞬时速率。

文本以可见输出的生产计数为基准；音频以最终解码产生的有效媒体时长为基准。服务器的最终生产计数只能用于容量估计，不能加入客户端库存。不能把各阶段 throughput 相加，也不能把客户端 pacing 后的交付速率直接视为系统容量。

低需求、主动暂停或网络消费限速时，观测输出量可能由需求限制。此时不能把短窗口实际输出速率当作可用容量下降的充分证据；需要有适用范围的校准模型和估计置信度。无有效容量依据、估计过期或超出校准范围时使用 FCFS，待重新具备证据后再开启优化。

预先冻结估计窗口、有效样本条件、置信界与回退策略；记下 Γ 点估计和用于约束的保守估计。完整报告预测误差和 Γ 高估导致的断流，容量条件是必要约束，不是无断流的数学充分保证。

### 4.3 准入检查

对队首候选 j 检查：

\[
D(t)+r_j\le\widehat\Gamma(t)
\]

以及 native KV/执行资源约束。候选失败就保持等待，不先准入再通过暂停隐藏它的需求。若当前 W 仍满足容量约束，仅候选准入失败不等于已有 W 过载；此时无需破坏已有安全调度。

## 5 缓冲调度与 FCFS 回退

在 W 满足容量约束的前提下，保留 TokenFlow 的工作集选择与缓冲平衡思路，以客户端 H_i 与恢复开销选择暂停/恢复。容量可行也不意味着每次抢占安全，还必须满足单请求条件：

\[
H_i^{safe}>t_{hold}+\widehat t_{resume\rightarrow client}+\epsilon_i.
\]

不等待 buffer 耗尽才恢复；新请求按首输出需求、已有请求按剩余覆盖时间安排。具体排序规则需在实现前写成明确伪代码，并校验缓冲越少时紧迫性确实升高，不能仅照抄论文 U_i 的符号而忽略其排序语义。

### 5.1 进入回退

当当前 W 满足 D(t)>Γ(t)，立即停止新的缓冲驱动暂停、借用执行名额和优化式工作集扩张。Γ 无效时同样使用 FCFS，但日志区分 overload 与 capacity_unknown。

在合法的执行边界完成正在执行的 GPU 工作，撤销策略持有的暂停/准入预留，按原始到达顺序归还 runnable 请求给原生调度路径，清除残留的优先级覆盖。客户端 buffer 保持正常接收和消费，内容不能被丢弃或重新播放。

先完成安全切换，再恢复 native FCFS 的资源分配与内存准入。不能只设置 policy_suspended 就宣称已经回到原生 FCFS；必须核对 waiting/running、暂停集合、预留名额和 KV 生命周期。

### 5.2 回退中的准入与退出

过载期间不扩张优化工作集。未准入请求按 FIFO 等待；已准入请求继续由 FCFS 推进，不能因 D>Γ 停止所有计算而死锁。释放资源后按原生内存准入处理等待请求，并明确记录它属于 FCFS 服务阶段，而不是容量满足时的流式承诺。

恢复缓冲优化前，重新用全部尚需生成的已准入请求检查 D≤Γ，不能漏掉仍暂停或暂不可运行的请求。进入过载回退没有宽限窗口；退出可要求连续若干有效估计满足容量和安全余量，降低切换抖动。退出滞回是实现选择，需在实验前固定，不声称为论文原文要求。

论文描述了 CPU offload 等待机制。第一版若仍采用 KV 保留暂停，就不能声称实现了该部分：新请求未分配 KV 前可在 CPU 请求队列等待；已经驻留的请求不等于已换出 CPU。严格复现 CPU offload 需另做状态保存与恢复实现。

## 6 实验臂与测量

文本、音频分别执行三个臂：

| 臂 | 客户端消费 | 服务端策略 |
|---|---|---|
| A0 | 到达即展示/播放，无主动初始积累，记录物理播放队列 | 原生 FCFS |
| A1 | 客户端接收缓冲与约定消费速率 | 原生 FCFS |
| A2 | 与 A1 完全相同 | 客户端 buffer 调度，容量不满足时退回 FCFS |

主要比较 A2 对 A1，A0 用于观察消费策略的影响。所有臂关闭新增阶段接收缓冲与服务端文本 pacing，使用相同模型、GPU、KV 预算、执行容量、驻留上限、chunk 配置与采样设置。若采用执行 K/驻留 R 适配层，A1/A2 必须相同，并称为资源对齐 FCFS；未经适配的原生基线另列，不能只让暂停臂获得 R>K。

文本主指标按论文 Eq.(1)(2)，音频按相同收益与惩罚结构替换为媒体时长，分别报告，不合并总分。10%/20% 最终长度阈值仅用于离线评价，在线控制不得访问未来真实输出长度。旧 soft_ttft_v2 和 3.3 等价系数不作为本轮默认主指标。

同时报告启动延迟、累计/最大断流、完整率、SLO goodput、原始生成吞吐、有效输出吞吐、客户端尾部排空、暂停恢复成本。观察分母、超时与失败处理预先固定；不能只统计成功请求。无固定 20% 收益门槛，以配对效应、置信区间和连续性代价报告结果。

新增容量图：D(t)、Γ(t)、|W|、等待请求数、调度模式和切换原因。另报告优化/回退驻留时间比例、超限检测到 FCFS 生效延迟、回退期间新主动暂停数，以及回退前后队列次序。

## 7 验证顺序与验收条件

1. 请求速率传播：检查客户端 HTTP payload、服务端入口、各阶段请求元数据和全局 W 表中的相同 r_i。错误或缺失速率明确报错。
2. 库存来源隔离：客户端 buffer 为零且 Q01/Q12 很大时不能获得暂停信用；客户端反馈缺失/过期也不能退回阶段库存。保持客户端轨迹不变，任意改变阶段库存，库存信用结果应不变。
3. 客户端守恒：接收=消费+剩余；无丢失、重复或重排；EOS 后排空；反馈老化、断连、attempt 切换均正确处理。
4. 工作集核算：暂停、恢复、等待 chunk 不改变需求总和；三个音频阶段只计一次；完成/取消才释放相应计算需求；并发准入不越界。
5. 容量边界：构造 D<Γ、D=Γ、D>Γ；验证 Γ 突降、估计过期、低需求窗口、候选准入失败与真实工作集过载的区别。
6. 回退完整性：已有暂停与在途 batch 时触发过载；检查无新主动暂停、无状态丢失、原始到达次序、KV 分配安全和持续进展。固定过载状态下与独立 FCFS 的选择轨迹对照。
7. GPU 机制：已有长请求先积累客户端缓冲，再注入新请求，记录“决策→实际暂停→新请求执行→恢复→客户端新内容”。文本和音频分别通过。
8. 性能：分别测试可行稳态、可行但突发拥塞、持续过载、容量下降后恢复。至少 5 个配对种子，开放环同轨迹，顺序随机；无缓冲时的突发作为边界案例。

阶段接收库存隔离、速率端到端传播、容量超限 FCFS 切换三项均为正式性能实验的前置条件。仅文档修订或 CPU 测试通过不代表 GPU 机制成立。


## 8 四小时实现进度与边界（滚动更新）

## 10 实际算法口径与原生基线参考

控制循环每轮保留已有执行名额拥有者，首先检查全局 W/Γ 和反馈时效。只对解码边界且具有有效客户端信用的执行请求考虑主动暂停。恢复保护量为配置的恢复到客户端时间、固定余量和近期执行迭代开销之和；暂停请求根据最新客户端收取/消费反馈更新覆盖时间，提前至少 0.5 秒争取恢复名额。只有另一个执行请求拥有足够缓冲，才交换执行名额；否则在临界条件下退出主动调度。空余名额先交给已驻留的待执行请求，再由原生调度器准入新请求。所有容量、KV 与 FCFS 切换均保留独立日志。

必须区分“原生 chunk 就绪后等待执行”与“策略主动暂停”。音频初版曾错误地把未取得执行名额的原生请求加入暂停集合，导致频繁保护回退。修复后只有实际安全换出的执行请求才进入暂停集合；相关空缓冲与驻留等待测试已经加入。第一版音频目录及错误审计保留，不参与最终重复结果。

文本与音频的 Γ 分别来自独立校准：文本约 182.17 可见 token/s，乘安全系数后约 154.85；音频约 7.80 媒体秒/墙钟秒，乘系数后约 6.63。文本 12 请求的总需求为 120 token/s，可以全部进入 W；音频 12 个 1× 请求总需求为 12，因此通常只能先准入 6 个。这一容量准入差异本身会改变音频启动等待和断流，不能将全部收益归因于主动暂停。

补充原生参考 `text_native_reference_k16`：同一冻结的第 0 组 12 请求，在 Thinker 原生 max_num_seqs=16、未启用文本适配器时全部完成，平均启动 0.174 秒，原始吞吐 361.26 token/s，客户端 QoS 11.90。它的启动与原始吞吐优于 K=4 缓冲实验。因此 K=4 五组结果是资源受限排队场景下的机制验证，不证明该原型全面优于框架原生配置。该参考只有一组，不用于稳定尾延迟或总体收益外推。

音频输出长度使用显式 `sampling_params_list`：Thinker 上限 128，Talker 上限 384，Code2Wav 保持其长度上限；正常播放速率 1×。顶层 max_tokens 只覆盖 Thinker，不限制 Talker；早期超长预热已终止且确认三个阶段排空。使用有界音频请求是固定长度生成实验，并不保证语音在语义完整句末停止。
