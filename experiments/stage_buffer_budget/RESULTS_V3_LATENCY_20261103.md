# 实验二 V3：缓冲分数归因与逐类流式延迟

以下仅对已经冻结的 20 条和 32 条纯文本、单种子、K16/R64 成对试跑做分析，不新增 GPU 运行。原始结果、评分、负载哈希、运行源码版本见 [20 条主报告](RESULTS_V3_20261103.md)和 [32 条负载消融](RESULTS_V3_LOAD_ABLATION_20261103.md)。重算命令：

```bash
python3 experiments/stage_buffer_budget/analyze_latency_v3.py \
  /home/zhongyu/research_reports/stage_buffer_v3_20261103_tokenizer_fix \
  /home/zhongyu/research_reports/stage_buffer_v3_20261103_burst32_leasefix
```

每个结果根目录生成 `latency_breakdown.json`。请求 TTFT 取 `results.json` 的 `ttft_s`；TPOT 是同一请求相邻两个客户端实际收到的文本 token ID 的时间差均值，再对请求取 P50/P95，每条请求权重相同。`gap P95` 则把所有相邻间隔合并后取 P95，包含同一 SSE chunk 内多个 token 的零间隔。P50/P95 均为最近秩分位数 `ceil(p*n)-1`。这里的传输 token ID 与流式分数采用的最终可见文本重分词单位不同，因此 TPOT 不能直接与效用单位数相乘。阅读断流是冻结评分器按 4.8 token/s 模拟时的空缓冲等待时间。另从 Stage 0 的逐 token output-produced 事件计算生产 TPOT，包含主动暂停期间的间隔；事件数和 token ID 数在两组全部策略中逐请求完全相符。全体请求完成；20 条的 4 条紧急请求、32 条的 16 条紧急请求均为 `standard`，其余 16 条宽松请求为 `loose`。

## 为什么仅缓冲得分很高

冻结评分器按客户端收到的每个**可见文本单位**计算 $U_i=\sum_j h_{i,j}w(B_{i,j})$。其中 $h$ 是相对于阅读时钟的迟到权重；$B$ 是这一单位到达后，**客户端已经收到但还要多久才能读完**的库存时间。`buffer_full_credit_s=10` s 内 $w=1$，之后按 `buffer_decay_s=20` s 线性衰减，库存到 30 s 时 $w=0$。如果模型 20 s 左右生成 512 个 token，用户按 4.8 token/s 读完约需 106.7 s；提前收到的大多数 token 面临几十秒未读库存，得分被削弱。服务器先存着、接近阅读时刻再发，客户端收到的未读量便接近零，$w$ 接近 1。

20 条试跑所有策略都交付同样 8316 个可见单位，且阅读断流为零；无缓冲组因未读权重只获得 1903.724 个加权单位，即 63.457/s，平均每请求客户端未读库存峰值为 74.10 s。仅缓冲组获得满额 8316，即 277.200/s，未读峰值均值为 0.424 s。首输出扣分分别是 3.736/s 和 3.667/s；所以总分从 59.722 升到 273.533，几乎全部来自 $w(B)$ 变大。32 条试跑的无缓冲和仅缓冲加权效用分别为 2275.118 与满额 8688，归因相同。

这里的“客户端已收到但未读”是指 SSE 网络交付已经完成，但按虚拟阅读时钟尚未读到。没有假设真实人类客户端一定缓存了这些字节；这是评分器模拟的阅读队列。仅缓冲时相同的文本暂存在**服务器前端队列，尚未发送**，所以不计入客户端 $B$。在已保存轨迹上去掉 $w(B)$ 的离线消融后，20 条仅缓冲相对无缓冲仅 **+0.025%**；32 条为 **−0.002%**。这是位置敏感的评分效果，不是额外 GPU 处理能力或阅读连续性改善。正式评价应同时记录服务器和客户端的未消费库存，并在新运行前冻结是否把总未消费库存纳入主指标。保留原冻结指标作为本轮结果，不事后调整权重制造收益。

主动暂停与仅缓冲相比另有明确因果证据：20 条紧急请求首输出达标从 0/4 到 4/4，32 条从 0/16 到 15/16；对应增分分别约 +1.34% 和 +5.42%。但这两组的暂停增益仍未达到 20% 目标，且没有音频双阶段、持续到达及多种子证据。

## 暂停次数与暂停收益归因

这里的暂停次数指实际发出暂停申请的**受害请求数**；完整链同时要求紧急请求真实入批、原请求释放暂停并重新产出。仅缓冲对照没有主动暂停。

| 负载 | 策略 | 暂停申请 | 完整链 | 峰值同时暂停 | 流式分数 |
|---|---|---:|---:|---:|---:|
| 20 条 | 仅缓冲 | 0 | 0 | 0 | 273.533 |
| 20 条 | 动态暂停 | 4 | 4 | 4 | 277.200 |
| 20 条 | 固定预算暂停 | 4 | 4 | 4 | 277.200 |
| 32 条 | 仅缓冲 | 0 | 0 | 0 | 274.653 |
| 32 条 | 动态暂停 | 16 | 16 | 16 | 289.538 |

与仅缓冲相比，20 条动态暂停的总分增加 3.667 效用单位/s：token 效用差为 0、阅读断流扣分差为 0、首输出违约扣分减少 3.667/s。32 条总分增加 14.885/s：token 效用差为 0、断流扣分差为 0、首输出违约扣分从 14.961/s 降到 0.062/s；两者的 0.015/s 差额来自逐请求分数的零下截断。增分全部出现在紧急请求类别，宽松请求贡献同为 273.067/s。

32 条紧急请求平均 TTFT 从仅缓冲的 9.801 s 降到动态暂停的 0.923 s，达标从 0/16 到 15/16；紧急端到端 P95 从 16.085 s 降到 8.120 s。宽松受害请求的端到端 P95 从 106.573 s 变为 106.601 s，增加 28 ms；按同一请求逐条相减，端到端延迟变化均值 +14 ms、P95 +172 ms。16/16 均满足 160 s 上限且阅读断流为零。实际暂停时间中位数 1.028 s、最大 2.050 s，不能把 100 ms 申请值当成暂停时长。

32 条负载下，在保持宽松请求效用不变的前提下，紧急请求的满额效用仅 16.533/s，而仅缓冲组已得 1.587/s；所以暂停的理论增分上限为 (16.533−1.587)/274.653 = **5.44%**。这批负载即使把 16 条紧急请求全部救回，也无法证明 20% 的暂停收益。不能靠事后增大首输出罚分权重宣称达到目标；需要事前冻结具有更高紧急有效工作占比、同时仍能正常排空且确实占满 K 的负载，并报告不拥塞、适度拥塞和过载区间的全部结果。

这仍是单种子、纯文本、两个集中到达点的成对试跑；本轮只证明该负载下的让位收益。更严格的暂停效应测试应事前冻结多组正常可排空的到达轨迹和独立种子，每组始终以**相同文本缓冲和放行节奏但关闭主动暂停**为主对照；模型、GPU 映射、K/R、KV 上限、SLO 元数据、输出长度与随机种子保持相同。逐请求配对计算紧急等待到入批、TTFT 违约、紧急端到端延迟、受害请求恢复到首个新 chunk、可读库存和断流；逐项分解分数差。无缓冲组只用于单独衡量放行节奏的影响。正式双阶段结论还需独立审计 Stage 0→1、Stage 1→2 已接收库存和音频播放断流。


## 文献复核与下一轮位置消融

复核 [TokenFlow §3.2、§7.1.3](https://arxiv.org/html/2510.02758v1)：原文在 token 生成时定义未消费库存，并按输出长度比例设置效用衰减阈值。本轮实现是在客户端收到时取库存、使用时间阈值，属于修改后的评分，不能称为直接复现。把 token 留在服务器会降低当前客户端库存计数，却不必改善阅读体验。

本轮冻结分数和表格保留。下一轮增加消费时间线、无库存权重敏感性及生成到消费的总积压诊断，避免把库存位置变化解释成吞吐能力提升。阶段库存与最终输出采用不同单位，须保留内容映射，不能把同一内容的不同表示相加。

详细的公平位置对照、三阶段 GPU 采样和待完成项见 [阶段间缓冲归因方案](EXPERIMENT_2_PIPELINE_ATTRIBUTION.md)。现有纯文本结果不能证明 Q01/Q12 的作用或三阶段 GPU 利用率改善。
