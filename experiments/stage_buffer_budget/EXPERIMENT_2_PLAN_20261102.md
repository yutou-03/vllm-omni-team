## 1. 研究问题与主对照

在相同模型、物理 GPU、阶段映射、KV 池字节上限、到达轨迹和种子下，能否把已生成的阶段输出按请求保序暂存、控制释放，在宽松 SLO 的运行请求拥有足够库存时暂停其当前阶段执行，使紧急请求入批，并在库存耗尽前恢复原请求？目标是在正常负载的性能拐点附近，相对**未经缓冲或主动暂停修改的原生调度**，使按客户端消费口径计的流式有效吞吐争取提升约 20%，且不显著损害原请求的断流、尾延迟及分层 SLO。

主对照为原生 `native_fcfs`，不加载实验二控制器、不加阶段接收队列或释放闸门。固定水位和动态水位使用相同的缓冲实现；Stage 0-only、Stage 1-only 与两阶段联合是机制消融。可另做“缓冲开启、暂停关闭”的**诊断**，仅用于拆分缓冲与暂停贡献，不替代原生主对照。

资源公平性须显式审计：保留 KV 但让新请求入批，需要执行名额 `K` 与最大驻留数 `R>K` 分离。原生代码没有这一分离能力。主对照通过部署参数使可执行请求上限与策略的 `K` 相同，物理 KV 池字节完全相同；同时在报告中列出原生实际驻留上限 `K`、实验策略驻留上限 `R` 与真实峰值，不能声称两个上限语义完全相同。若这项结构差异足以影响解释，再运行相同 `K/R` 但关闭暂停的诊断对照。

## 2. 当前数据通路与计划插入点

当前 Thinker→Talker、Talker→Code2Wav 都经 `SharedMemoryConnector`：发送阶段把 chunk 的张量转为 CPU 可序列化数据，按 `(物理请求尝试, 阶段, chunk_id)` 写到本机 `/dev/shm`；下游 `OmniChunkTransferAdapter` 的后台接收循环按顺序 `get`，反序列化并立即更新该请求的输入状态。Talker 把收到的文本/embedding 并入累计 payload，满足 conditioning gate 后进入调度；Code2Wav 把收到的新 codec 帧设为输入并开始转换。现状没有“接收后可控释放”的独立队列，下游常在收到后随即取用。

计划在**下游接收进程内**、`get` 成功之后、更新模型可见输入之前，为每个物理执行尝试插入有界 FIFO：

```text
上游完成 chunk → /dev/shm 已发布 → 下游 get 成功 → 接收进程的 CPU FIFO
                                              ↓ 按门控释放
                                    原有 payload/输入更新 → 下游模型取用
```

该 FIFO 存的是 embedding/codec 输出数据，**不是 KV**。接受 chunk 时记录 `received`，放行到原有输入更新路径时记录 `released`，模型选择 conditioning 位置或开始 codec 转换时记录 `consumed`。每个尝试和 chunk 身份必须保持连续、唯一、保序；超限停止预取并实行背压；取消或重启时只清理对应尝试。未 `get` 成功的 `/dev/shm` chunk 不计安全库存。队列容量同时限制 chunk 数、conditioning 位置/codec 帧数和实际主机字节数，记录峰值及排队时长。释放可以按原 chunk 粒度进行；首版不拆 chunk、不修改模型输出。

记账不变量按每个物理尝试、chunk 身份及有效输出单位分别检查：`sent ≥ received ≥ released ≥ consumed`；终止后解释所有差额（完成、取消、被动重启或待清理），不可跨尝试凑平。原有接收代码把 `get_req_chunk` 前移并立即合并 payload，实施时要分开“已预取游标”和“已释放游标”，不能让未放行的 chunk 被现有 scheduler 视为输入。Stage 0 库存单位为可用 embedding conditioning 位置，排除 prompt 行和已选择位置；Stage 1 为新的 codec 帧，排除重复 left context，开始转换即计为已消费。控制器只能依据已收到、尚未取用的同尝试数据和实测恢复成本作暂停预算。

### 释放策略与人为蓄水

缓冲积累是**有意识的控制动作**。对首次可见文本/首段音频尚未交付的请求，优先立即放行必要的首包，避免额外拖慢 TTFT/TTFP；对已建立流且 SLO 宽裕的候选请求，允许上游在短窗口内比下游多生产一些数据，再按下游需要放行。释放速度按下游实际取用率、当前下游/客户端库存、首段和完整响应截止时间确定，不能直接把 Talker 或 Code2Wav 的内部输入速率设为人类 4.8/3.3 token/s。若刻意延后下游导致其空转、TTFP 上升或 E2E 恶化，按真实代价计入，不能从日志中隐藏。

Stage 0 暂停 audio 请求时，Stage 1 继续从 Thinker→Talker 队列取用；Stage 1 暂停时，Stage 2 继续从 Talker→Code2Wav 队列取用。只经过 Stage 0 的 text 请求没有阶段间队列，需用**已被客户端收到的文本库存**保护其阅读流；单独统计这一支路，不能把它写成 Stage 0→1 缓冲收益。同一 audio 请求的两个阶段首轮禁止同时主动暂停；联合策略先以全局请求状态协调两个本地决策，防止重复使用同一段下游播放时间。

## 4. 流式服务下的有效吞吐率

原始 TokenFlow 分别定义综合 QoS（加权 token 减 TTFT 和 rebuffer 惩罚）和评测中的加权有效 token 吞吐。实验二的主指标先固定成**满足首输出 SLO 的、逐单位计价的流式有效吞吐**：客户端收到后按 4.8 token/s 阅读文字，按真实可播放时长 1× 播放音频；3.3 token/s 仅用于把音频内容秒数换成文本等价单位。`B_i` 是客户端已收到而未消费的库存覆盖秒数，不是阶段队列库存。对 token/chunk 的及时性与过量库存使用预先冻结的 `h_i(lag)∈[0,1]`、`w_i(B)∈[0,1]`，并单独扣除断流秒数：

```text
G_stream = (1 / T_arrival) × sum_{全部 offered i}
           1{完整输出、首输出满足其 SLO}
           × max(0, sum_j m_ij × h_i(lag_ij) × w_i(B_ij) - μ × rebuffer_i)
```

文本 `m_ij=1`，音频 chunk `m_ij=3.3×可播放秒数`。`lag` 以客户端理想消费时间线为参照；`w` 按缓冲秒数在安全储备范围内满分、过量时线性衰减。不能把尚未到达客户端的阶段 chunk 计为用户侧输出。`h`、两段缓冲阈值及 `μ` 的具体值须在独立校准中根据无暂停抖动、可接受断流和实测暂停/恢复时长冻结，所有策略共用。报告 TokenFlow 原式口径的辅助结果、原始 token/s、音频内容秒/s、E2E 及完整请求达标率；主指标不得单独掩盖 text/audio 分层退化。目标 `G_dynamic/G_native ≥ 1.20`，以配对种子的 95% 置信区间检验，并公布绝对差。

现有 `sse_client_extended.py` 对音频已有 1× 播放模拟，对文本只离线计算固定速率的到期比例，且默认 20 token/s、2 s 首输出。正式比较前需把文本改成以 **4.8 token/s** 运行的可重放阅读器，并从冻结请求读取 TTFT/TTFP、迟到及缓冲参数；所有策略由同一客户端分析器按原始 SSE 重算，不使用当前硬编码的 `qualify()` 作为正式判定。

## 5. 暂停条件与两阶段协同

仅从已在运行、到达安全 decode/checkpoint 边界、已有可核对库存的请求中挑受害者。优先考虑 `loose` tier，但必须用**剩余**首输出、流畅度和 E2E 预算判断，不能仅凭 tier 标签暂停。紧急请求必须真实等待执行名额，且按其冻结的阶段预计剩余时间判断继续等待会损害其 SLO；常规请求不因“有库存”就被无谓暂停。

安全窗口按墙钟而非请求的 `max_hold_s` 计算：等待下一个可暂停点、紧急请求实际进入并完成足以释放名额的执行切片、申请到释放的超期、原请求重新入批以及恢复后的首个 chunk，均使用本次独立测得的高分位上界和余量。只有已接收的阶段队列和客户端已接收内容可提供覆盖。两个阶段各自用本地库存、消费速率和 checkpoint 测量判定；联合控制需把 Stage 0 延后传给 Stage 1/2 的影响计入音频首段及尾部，并避免同请求双重记账。100 ms 只是申请上限，不是墙钟保证。

固定策略用各阶段校准出的保守覆盖水位；动态策略在同一水位基础上加入当前批次形状、检查点等待、紧急请求执行耗时、恢复首 chunk 和 SLO slack。不得通过直接降低阈值凑触发次数。KV 始终驻留 GPU；如果 KV 池接近满额、没有额外驻留空间，则跳过暂停并记录原因。

## 6. 实施顺序和退出条件

1. **独立标定与负载冻结。**当前裸服务测四层 TTFT/TTFP/E2E、阶段速率、客户端消费和原生 KV 占用；保存源码 commit、部署、GPU 映射、请求及输出哈希。生成带标准/宽松 tier 的不可变 JSONL。此阶段不估计策略收益。
2. **接收队列及门控。**只改两条阶段边的下游接收适配器，增加 FIFO、释放闸门、容量/字节限制、尝试隔离和事件。CPU 测试覆盖顺序、重复接收、溢出、取消、重启、首包、EOS。先以门控关闭验证输出与原生完全一致。
3. **蓄水机制 GPU 烟测。**在真实 GPU 上选择已有首输出且 SLO 宽裕的候选，请求其上游先生产数个 chunk；逐时刻证明 `received - consumed` 实际变大，释放闸门按计划喂给下游，客户端流不丢包。若没有增长，分别测上游生产/下游消费速度及接收预取能力，再改蓄水窗口，而非降低暂停安全阈值。
4. **完整暂停事件链。**用冻结的宽松受害者和紧急请求证明 `hold_requested → urgent_keep_admitted（受害者未同轮执行）→ hold_released → first_rescheduled → first_new_chunk`；核对同尝试 chunk 连续、输出哈希/长度、接收/释放/消费守恒、KV 块归属和实际墙钟超期。任一步缺失，只报告机制失败或试跑。
5. **正常负载拐点试跑。**裸服务先扫描共同绝对 QPS，选能自然排空、KV 不因饱和触发大量被动抢占、紧急等待与宽松运行请求有重叠的点。预计每层标准/宽松请求都应有观测样本；若原生基线几乎无延迟损失，则增加到达密度而不修改 SLO；若大多不可达，则降低负载。
6. **成对正式比较。**每个负载点使用同一负载文件、模型、GPU、KV 池、token budget、随机种子；按随机顺序运行原生、固定、动态及必要的 Stage 0-only/Stage 1-only 消融。每组 warmup→排空→开放环测量→彻底排空；至少 5 个配对种子，样本不足或置信区间过宽则增加。保存完整客户端 SSE、阶段事件、服务器日志、GPU/KV 状态、配置、代码与负载哈希、分析脚本和图。

正式报告必须分层给出 text/audio、short/long、standard/loose、紧急/受害者的 `G_stream` 贡献、首输出违约、E2E 违约、客户端最大/累计断流、原请求恢复首 chunk、实际暂停超期和尾延迟。仅当完整机制链与输出守恒成立，且主指标提升达到约 20% 目标 且受害者体验没有显著恶化，才称为实验二性能收益。导图“超过 512 token 后预测更准”另建足够跨越 512 的校准/验证集，比较前后误差；不从当前 64-token 主负载推断。

## 7. 计划制定时的风险记录（后续执行见第 0 节和结果报告）

- 历史 2026-10-19 的 1.2×/3× 运行没有真实暂停；Stage 0/1 在决策点的接收端库存仅覆盖 34.7/14.2 ms。新 FIFO 必须证明已收到库存增长和下游真实持续消费。
- 当前 `stage_buffer_controller_budget.py` 按物理执行 ID 的尝试隔离修复仅通过 CPU 测试，尚未在 GPU 验证。
- `small_hold_probe.py` 只能在同步调度边界释放。较大 prefill 可跨越 100 ms 请求期限；应先度量并限制紧急切片的最长墙钟，或在风险无法界定时不申请暂停。
